## "MetaTrader updated — is anything broken?"

The operator's question, and the right one: every control this project uses is
identified by a value measured on one build, and an update is the ordinary event
that moves them. The order path already fails closed when a control disappears,
but it fails at the moment of trading.

`python -m auto_trade terminal-check` moves that discovery forward. It resolves
the terminal, opens the order dialog, reads the control tree, closes the dialog,
and reports each expected identifier as present, drifted, absent, or ambiguous.
It has **no code path that uses a final control**, so it cannot place an order.
`--compare` diffs against the recorded history in `logs\terminal_check.json` and
names any control whose value changed, so the question stays answerable after
the fact instead of from memory. Reports are appended per build, never
overwritten.

Run on this terminal, it reported **`OK`, 13 controls, none drifted and none
missing**. Every identifier measured on 6184 — `10408`, `10409`, `10325`,
`10333`, `10334`, `10336`, `10328` — is still correct on 6230. **The update broke
nothing.** The final controls are matched by name *and* id, so both survived.

The probe found a bug in itself on the first run: it reported `New Order` as
missing, because it was looking inside the order dialog for a menu item that
lives on the main window. That is the failure mode a probe must not have — an
operator would go hunting for a break that does not exist — so `New Order` is now
probed where it actually is, with a test that pins the two apart.

## A real defect: the wrong terminal could be driven

Five MT5 terminals were running and **four shared the window title
`Alpari-MT5-Demo`**. `MT5WindowManager.find()` matched windows by title and took
`matches[0]`, so it selected an account by enumeration order. The demo check in
`connect()` would have passed for all four, because every one of them is a demo —
the guard meant to stop this project driving the wrong account did not stop it.

It happened to pick the right PID (5680) by luck of enumeration order, which is
exactly why this survived the 2026-09-28 session: on a machine with one terminal,
`matches[0]` is correct by definition.

The fix: `WindowsTerminalDiscovery.resolve` now returns the process id it
resolved, and the window is selected by that process id. A title match finding
more than one window is **refused**, and the refusal names every candidate. There
is no flag to pick the first. The instance name can only narrow a set the
executable path already selected, never select on its own.

This is the second time in two sessions that a property held on one machine was
not a property of the code. It is recorded in
[MT5_INTEGRATION.md](MT5_INTEGRATION.md) as a defect with the reasoning intact.

## What was done

### The authenticated local API

`src/auto_trade/interfaces/api.py`, served by `python -m auto_trade api`.

The design question was what a local API is *for* in a project whose two
commitments are that a click proves nothing and that every path which changes an
account is operator-initiated. The answer that follows from those commitments:
it can read state and operate the durable stop, and that is all. So the surface
is authenticated on every route, binds loopback only, and has no endpoint that
places, modifies, or closes an order.

Three decisions worth knowing about:

1. **Reads require the token here, and do not on the dashboard.** The dashboard's
   `GET` routes are open, which is fine for a page a person opened. A program
   that calls on a schedule is a different case: a status feed that can be read
   or spoofed by anything else on the machine is not a status feed. This is the
   one place in the project where a read is authenticated.
2. **The token is refused in a query string** (`400`). A URL is written to proxy
   logs, history, and `Referer`. The dashboard tolerates `?token=` because a
   browser fetch cannot always set a header; a program can, so this surface has
   no such excuse.
3. **A token is mandatory.** `build_api_server` refuses to start without one
   rather than generating a token nobody can read, which would be a service
   answering `401` forever.

An account-changing route is refused with `403` and a message naming the CLI,
not with a bare `404`, so a caller that guesses learns the boundary instead of
trying verbs until something answers.

`LocalApiClient` in `src/auto_trade/infrastructure/api_client.py` is included so
a caller does not re-implement the loopback, redirect, and authentication rules.
It is a reader: it has no method that could place an order, which is asserted by
a test so the boundary stays visible in the code.

### A shared network policy, and a real defect it exposed

`LoopbackOnlyRedirectHandler` moved out of `signals/http.py` into
`infrastructure/net.py`, because the new client needs the same redirect refusal
and two copies of a security policy will eventually disagree. The signal
provider's behaviour is unchanged and its tests still pass; the redirect refusal
is now a `NonLoopbackRedirectError` that each caller converts to its own error
type, so it still reports as a policy refusal rather than as a dead host.

While reading the dashboard handler for this, one real defect turned up:
`_read_body` was called *after* the route lookup, so a `POST` to an unknown route
answered `404` with its body still in the socket buffer. Under HTTP/1.1
keep-alive that desynchronises the next request on the same connection, and the
existing test only covered the case where a route existed and the token was
wrong. The drain now happens before routing, on the API as well, and both cases
have tests.

### The bilingual documentation contract caught two gaps

`docs/API.md` and `docs/fa/API.md`, with the pair added to `PAIRS` in
`tests/unit/test_documentation.py`. Registering the pair immediately failed on
two real gaps: the Persian page did not quote the literal refused route, and
neither README listed the new page. That is the contract working as intended,
and it is the reason to register a pair at the moment it is written.

The new pair is also added to the two existing documentation tests, so a
translation that keeps the prose but loses the refusals, or mistypes an
identifier an operator compares against real output, fails the build.

## What was deliberately not done

- No endpoint that places, modifies, or closes an order, anywhere.
- No `POST /api/v1/signals`. A read route answers `405` to a `POST`, so a
  monitoring client cannot become a signal source by changing one method.
- No TLS. `https` is accepted by the client for a proxy in front of it, and the
  server does not terminate TLS.
- No rate limiting or lockout on repeated bad tokens. The boundary is loopback
  plus a token; a lockout would be a new denial-of-service surface against a
  control that must always be reachable, and it is worth a decision rather than
  a default.
- No live or funded account was used, and none is in scope at any step.
- No hedge, partial close, or modify.
