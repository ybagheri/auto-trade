# API محلی

یک HTTP API فقط‌خواندنی، احرازهویت‌شده با توکن و محدود به لوپ‌بک، برای
برنامه‌های همین ماشین. تنها با کتابخانه‌ی استاندارد پایتون ارائه می‌شود، بنابراین
طراحی بدون وابستگی زمان‌اجرای پروژه حفظ می‌شود.

```powershell
$env:AUTO_TRADE_API_TOKEN = "<token>"
python -m auto_trade api --port 8766
```

`python -m auto_trade api --print-token` یک توکن تازه تولیدشده را برای اپراتوری
چاپ می‌کند که هنوز یکی پیکربندی نکرده است.

## چرا این وجود دارد و چه چیزی نیست

[داشبورد](DASHBOARD.md) به یک انسان خدمت می‌کند که خودش صفحه را باز کرده است.
این به یک پروسه خدمت می‌کند: یک اسکریپت مانیتورینگ، یک خط وضعیت در برنامه‌ای
دیگر، یا ابزار دوم اپراتور. همین تفاوت است که هر چیز زیر را تعیین می‌کند.

**این execution API نیست.** هیچ مسیری اینجا سفارشی ثبت، تغییر یا نمی‌بندد و
هیچ‌کدام هم قابل وادار کردن به این کار نیستند. اپراتوری که می‌خواهد سفارشی ثبت
شود، CLI را اجرا می‌کند که همه‌ی دروازه‌ها را دوباره اجرا می‌کند و
`--confirm-demo` را دستی می‌طلبد. [اجرا](EXECUTION.md) را ببینید.

**از شبکه در دسترس نیست.** سرور هر آدرس bindای را که `127.0.0.1`، `::1` یا
`localhost` نباشد رد می‌کند، و کلاینت هر endpointای را که یک URL صریح لوپ‌بک با
`http`/`https` نباشد رد می‌کند. میزبان شبه‌مانندی مانند
`localhost.example.com` با مقایسه‌ی تحت‌اللفظی رد می‌شود، نه با پسوند. هیچ
flag‌ای برای دور زدن این بررسیِ bind وجود ندارد؛ اگر واقعاً دسترسی از راه دور
لازم است، از یک تونل SSH یا proxy با احراز هویت مستقل خودش استفاده کنید.

**تنها سطح محلی‌ای است که یک خواندن به توکن نیاز دارد.** endpointهای `GET` داشبورد
روی لوپ‌بک بازند، که برای صفحه‌ای که کسی آگاهانه باز کرده قابل قبول است اما برای
برنامه‌ای که طبق زمان‌بندی فراخوانی می‌کند نه. یک agent مانیتورینگ که «kill switch
غیرفعال است» یا «یک تلاش تسویه‌نشده وجود دارد» را گزارش می‌کند یک جریان وضعیت
است، و یک جریان بدون احراز هویت را هر چیز دیگری که روی ماشین اجرا می‌شود می‌تواند
بخواند یا جعل کند.

## ویژگی‌های ایمنی

**هر مسیر به توکن نیاز دارد، شامل خواندن‌ها.** توکن غایب یا اشتباه `401` می‌گیرد و
درخواست هیچ چیزی را تغییر نمی‌دهد. احراز هویت *پیش از* مسیریابی بررسی می‌شود، پس
یک فراخوان بدون احراز هویت نمی‌تواند از تفاوت `401` و `404` وجود مسیرها را بفهمد.

**توکن در رشته‌ی پرس‌وجو رد می‌شود.** `?token=...` مقدار `400` می‌گیرد. یک URL در
لاگ‌های proxy، تاریخچه‌ی مرورگر و هدرهای `Referer` نوشته می‌شود. داشبورد این فرم را
تحمل می‌کند چون یک fetch دست‌نویس از مرورگر همیشه نمی‌تواند هدر بگذارد؛ یک برنامه
می‌تواند، پس این سطح چنین بهانه‌ای ندارد. کلاینت آن را فقط در هدر
`X-Auto-Trade-Token` می‌فرستد.

**توکن بدون خروج زودهنگام مقایسه می‌شود**، با همان `constant_time_equals` که منابع
WebSocket و named pipe استفاده می‌کنند، پس یک فراخوان نمی‌تواند با زمان‌سنجی پیشوندی
از توکن را یاد بگیرد.

**توکن اجباری است.** `build_api_server` بدون توکن اجرا نمی‌شود، به‌جای تولید یک توکن
تصادفی که هیچ‌کس نمی‌تواند بخواند، که سرویسی بود که بی‌صدا برای همیشه `401` جواب
می‌داد. یک `AUTO_TRADE_API_TOKEN` خالی یعنی «بدون احراز هویت» نیست؛ یعنی فرمان با
خطا خارج می‌شود.

**مسیر تغییردهنده‌ی حساب با دلیل رد می‌شود، نه با `404` خالی.** فراخوانی که
`/api/v1/execute` را حدس بزند، `403` می‌گیرد که CLI را به‌عنوان مسیری که هنوز وجود
دارد نام می‌برد. نکته این است که فراخوان مرز را یاد می‌گیرد به‌جای اینکه تا جواب
دادن به هر فعل دیگری امتحان کند.

**درخواست ردشده اتصال را قابل استفاده رها می‌کند.** بدنه‌ی درخواست‌ها پیش از هر
پاسخی، شامل رد شدن‌ها و مسیرهای ناشناخته، تخلیه می‌شوند، چون بدنه‌ی خوانده‌نشده در
بافر سوکت می‌ماند و درخواست بعدی روی همان اتصال keep-alive را از وسط بدنه پارس
می‌کند.

**اقدامات کنترلی حسابرسی می‌شوند.** هر دو مسیر یک رکورد حسابرسی `local-api`
می‌نویسند و هیچ‌کدام توکن را ندارند. داشبورد اقدامات کنترلی خودش را حسابرسی نمی‌کند؛
این سطح می‌کند، چون *برداشتن* توقف همان اقدامی است که ارزش زیر نظر دارد — همان یکی
که یک توقف را برمی‌دارد.

## endpointها

همه‌ی مسیرها زیر `/api/v1/` هستند و همه‌ی آن‌ها به هدر نیاز دارند.

| متد | مسیر | کاربرد |
| --- | --- | --- |
| GET | `/api/v1/health` | زنده‌بودن و وضعیت kill switch |
| GET | `/api/v1/status` | مسیرهای ترمینال، flagهای ایمنی، شمارش‌ها |
| GET | `/api/v1/risk` | فهرست مجاز و محدودیت‌های ریسک |
| GET | `/api/v1/positions` | وضعیت مشاهده‌ی پوزیشن، یا دلیل در دسترس نبودنش |
| GET | `/api/v1/signals` | فایل‌های سیگنال در انتظار |
| GET | `/api/v1/executions` | رکوردهای دفتر اجرا، جدیدترین اول |
| GET | `/api/v1/metrics?tail=N` | شمارنده‌ها و تأخیر هر فاز، N با سقف ۵۰۰۰ |
| GET | `/api/v1/logs?tail=N` | tail لاگ حسابرسی، N با سقف ۵۰۰۰ |
| POST | `/api/v1/emergency-stop` | فعال‌کردن توقف پایدار |
| POST | `/api/v1/resume` | برداشتن توقف |

عمداً هیچ `POST /api/v1/signals` وجود ندارد. یک مسیر فقط‌خواندنی به `POST` با `405`
پاسخ می‌دهد به‌جای اینکه چیزی بنویسد، پس یک کلاینت مانیتورینگ نمی‌تواند با عوض کردن
یک متد به منبع سیگنال تبدیل شود.

هر خواندن با همان `StatusReporter` که داشبورد استفاده می‌کند ارائه می‌شود، پس دو
سطح نمی‌توانند در آنچه گزارش می‌دهند اختلاف داشته باشند. هیچ‌چیز اینجا پنجره‌ی MT5 را
باز یا هدایت نمی‌کند.

## کلاینت

`LocalApiClient` در `infrastructure/api_client.py` هست تا یک فراخوان مجبور نباشد سه
قاعده‌ای را که این فراخوان را ایمن می‌کنند دوباره پیاده کند.

```python
from auto_trade.infrastructure.api_client import LocalApiClient

with LocalApiClient("http://127.0.0.1:8766/api/v1", token) as client:
    print(client.status()["safety"]["kill_switch_active"])
    print(client.metrics(tail=500)["counters"]["unresolved_attempts"])
```

این یک *خواننده* است. هیچ متدی ندارد که سفارشی ثبت، تغییر یا ببندد، و سرور به هر
حال آن مسیرها را رد می‌کند. `401` یا `403` به‌عنوان «توکن رد شد» گزارش می‌شود نه
به‌عنوان یک قطعی، پس فراخوان یاد نمی‌گیرد دوباره تلاش کند. ریدایرکتی که لوپ‌بک را
ترک کند رد می‌شود به‌جای دنبال کردن، و این همان سیاست مشترکی است که provider سیگنال
استفاده می‌کند، پس این دو نمی‌توانند درباره‌ی آن اختلاف داشته باشند.

## این پاسخ‌ها چه چیزی نیستند

`200` از `/api/v1/status` یعنی درخواست مجاز بود و وضعیت خوانده شد. یعنی ترمینال در
دسترس بود، یا حساب demo است، یا چیزی سالم است، نیست. `/api/v1/positions` وقتی
snapshot غایب یا stale باشد `UNAVAILABLE` را همراه با دلیل برمی‌گرداند، پس «پوزیشنی
وجود ندارد» و «نمی‌توانم پوزیشن‌ها را ببینم» از هم قابل تفکیک می‌مانند.
`/api/v1/metrics` یک فاز اندازه‌گیری‌نشده را `null` با `measured: false` گزارش
می‌کند، هرگز صفر. هیچ رقمی در این API یک معامله را پذیرفته‌شده گزارش نمی‌کند: هیچ‌چیز
در این برنامه پذیرش بروکر را مشاهده نمی‌کند، و دفتر اجرا نتیجه را تسویه می‌کند.
[سنجه‌ها](METRICS.md) و [بازیابی](RECOVERY.md) را ببینید.

## تست‌ها

`tests/unit/test_api.py` به‌جای فقط مسیر خوش‌بینانه، رد شدن‌ها را پوشش می‌دهد: اینکه
هیچ مسیری در جدول خواندن بدون توکن جواب نمی‌دهد (پارامتری روی همان جدول، پس مسیر
تازه‌ای نمی‌تواند بدون احراز هویت اضافه شود)، اینکه توکن در رشته‌ی پرس‌وجو رد
می‌شود، اینکه بررسی bind و اجباری بودن توکن برقرار است، اینکه هر مسیر
تغییردهنده‌ی حساب با دلیل رد می‌شود، اینکه هر دو جهت کنترل بدون توکن حسابرسی
می‌شوند، و اینکه درخواست ردشده اتصال keep-alive را خراب نمی‌کند. این تست فقط روی
لوپ‌بک و پورت ۰ bind می‌شود، پس نه به MT5 نیاز دارد و نه به پورت ثابت.
